# Sync-Storm Rate-Limit Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop `GenericProvider`'s sync traffic from blowing up super-linearly as simulated user count grows, which the benchmark in `test/dummy/bench-user-scaling.ts` measured causing message counts to reach 20-200x the theoretical linear cost at N=100 (see `docs/superpowers/specs/2026-07-26-dummy-benchmark-scaling-design.md`).

**Architecture:** Three tasks, discovered incrementally as each one's own verification revealed the next real bottleneck (this plan was updated mid-execution to reflect that - see the design spec's Addendum and Part 4 for the full story):
1. Extract a shared rate-limit helper out of `_sendSyncStep1()` (pure refactor, enables Task 2).
2. Gate `syncNow()`'s previously-uncapped full-state push behind that shared limiter. Measured impact turned out modest (~1.3x, not the originally-expected 5-10x) - still a legitimate standalone improvement, committed as such.
3. **The task that addresses the actual dominant cost:** suppress redundant SyncStep2 replies. Every reply to a SyncStep1 request is broadcast to the whole room (no transport here supports unicast), so N-1 peers can each independently reply to the same request, each broadcasting to N-1 recipients - an O(N²) reply pile-up per request, unaffected by Task 2's fix. Task 3 delays replies briefly and drops them if another peer's reply is overheard first (NACK-suppression), gated on a peer-count estimate so small rooms (where there's no "someone else" to rely on) aren't affected.

**Tech Stack:** TypeScript, Yjs, y-protocols/sync, lib0/encoding. No test framework in this repo — verification is via the two benchmark scripts under `test/dummy/` (`bench-sync-latency.ts`, `bench-user-scaling.ts`) plus a manual smoke test.

## Global Constraints

- No wire-format changes needed for this fix (this is pure trigger-frequency throttling, not a message-shape change) — breaking changes were pre-approved for this project but aren't used here.
- `dist/` is committed to git despite `.gitignore` (pre-existing tracked files, per `CLAUDE.md`) — every task that changes `src/index.ts` must rebuild it with `npm run build` and commit the result in the same commit.
- Do not touch `Transport` (`src/transport.ts`) or any provider under `src/providers/` other than what's already planned — out of scope per the design spec.
- Existing safety nets (sequence-number gap detection, exponential hash-mismatch backoff, the `c048682` reordering-suspicion suppression) must keep working exactly as before — this fix only changes how often `syncNow()`'s push fires, not the detection/backoff logic itself.

   * Reserve a slot in the sync rate limiter (max `_maxSyncRequestsPerWindow`
   * per `_syncRequestWindowMs`), recording the request if there's room.
   * Shared by `_sendSyncStep1()` and `syncNow()` so a burst of triggers from
   * different sources (periodic sync, hash-mismatch resyncs, gap-check
   * confirmations) draws from one combined budget instead of each having
   * its own uncapped or separately-capped allowance.

### Task 3: Suppress redundant SyncStep2 replies (NACK-suppression)

**Files:**
- Modify: `src/index.ts` (class fields near `_syncRequestWindowMs`; the `MESSAGE_SYNC` case in `_handleIncomingMessage`, currently at `src/index.ts:757-782`; two new private methods, placed just above `_trackRemoteSeq` at `src/index.ts:928`)
- Modify: `dist/index.js`, `dist/index.js.map`, `dist/index.d.ts.map` (regenerated by `npm run build`)

**Interfaces:**
- Consumes: `this.awareness.getStates(): Map<number, any>` (existing `y-protocols/awareness` API, already used elsewhere in this file) as a cheap live estimate of known room size; `this._send(data: Uint8Array): void` (existing).
- Produces: no new public interface. Two new private methods: `_scheduleSyncReply(reply: Uint8Array): void`, `_cancelPendingSyncReply(): void`.

**Context:** When peer A broadcasts a SyncStep1 request, every other peer in the room receives it and independently computes+sends a SyncStep2 reply (since `DummyHub`, and every other transport in this codebase, has no unicast — a "reply" is just another room-wide broadcast). If N-1 peers all have data A is missing, all N-1 reply, and each of those replies is itself broadcast to N-1 recipients: O(N²) traffic from a single request. Since all replies are broadcast, every peer already overhears every other peer's replies "for free" — this task uses that to suppress redundant ones: delay your own reply briefly, and if you overhear someone else's reply first, skip yours.

This was prototyped and measured directly (not just theorized) against both benchmark scripts before being written into this task — see the design spec's "Part 4" section for the full numbers. The two things that prototype proved matter and this task's steps encode:
1. The suppression window doesn't need to be large — 30ms was enough to collapse N=100 fan-out from a mean of ~286,591 messages to ~96,304 (and, more importantly, cut the worst-case from 835,956 down to 112,914).
2. Suppression **must** be gated on there being genuine redundancy (`awareness.getStates().size >= 3`, i.e. at least 2 other known peers) — without this gate, a 2-peer room can suppress its *only* viable reply and stall (reproduced directly: 30 consecutive hash mismatches, one peer stuck on an empty document).

- [ ] **Step 2: Add the schedule/cancel methods**

Add these two methods to `src/index.ts`, directly above the existing `_trackRemoteSeq` method (currently at line 928):

```typescript
  /**
   * Schedule a SyncStep2 reply after a short random delay instead of
   * sending immediately. If another peer's reply is overheard in the
   * meantime (`_cancelPendingSyncReply`), this reply is dropped as
   * redundant - the requester likely already got what it needed.
   */
  private _scheduleSyncReply(reply: Uint8Array): void {
    this._pendingSyncReply = reply
    if (this._pendingSyncReplyTimeoutId !== undefined) return
    const delay = Math.random() * this._syncReplySuppressionMs
    this._pendingSyncReplyTimeoutId = setTimeout(() => {
      this._pendingSyncReplyTimeoutId = undefined
      if (this._pendingSyncReply) {
        this._send(this._pendingSyncReply)
        this._pendingSyncReply = null
      }
    }, delay)
  }

  /** Cancel a pending suppressed reply, if any. */
  private _cancelPendingSyncReply(): void {
    if (this._pendingSyncReplyTimeoutId !== undefined) {
      clearTimeout(this._pendingSyncReplyTimeoutId)
      this._pendingSyncReplyTimeoutId = undefined
    }
    this._pendingSyncReply = null
  }

```
